# server-deadman

Внешний дед-ман для `guardlabs.online`.

Раз в 30 минут с инфры GitHub дёргает публичный штамп живости
<https://guardlabs.online/hb.txt> (его пишет на сервере cron `*/2`).
Штамп протух больше 15 минут или адрес не отвечает — тревога уходит
в Telegram **напрямую** через `api.telegram.org`, минуя наш сервер,
плюс падает job, и GitHub дублирует тревогу письмом владельцу репо.

Смысл в том, что сервер не может сообщить о собственной смерти.
Поэтому проверяющий обязан жить снаружи и не зависеть от проверяемого.

## Почему репозиторий публичный

Раньше этот workflow лежал в приватном репо на бесплатном тарифе.
За всё время существования расписание отработало **2 раза**: GitHub
почти не запускает cron-workflow в бесплатных приватных репозиториях.
Дед-ман молча молчал 83 дня (11.06 - 02.09.2026), и никто об этом не знал.
В публичных репозиториях Actions не тарифицируются и расписание отрабатывает.

Секретов в коде нет: токен бота и chat_id лежат в Secrets репозитория.
Штамп живости и так публичный и содержит только epoch/iso/hostname/uptime.

## Кто сторожит сторожа

На сервере крутится обратная проверка (`/root/scripts/deadman_watch.sh`, cron раз в час):
если сам дед-ман молчит дольше 4 часов, она пишет Стасу. Кольцо замкнуто —
чтобы тревога снова потерялась, отказать должны обе стороны сразу.

## Проверить живьём

    gh workflow run deadman.yml --repo sspoisk/server-deadman                      # зелёный при живом сервере
    gh workflow run deadman.yml --repo sspoisk/server-deadman -f test_alert=yes    # учебная тревога в Telegram
